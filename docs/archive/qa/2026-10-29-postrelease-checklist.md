# AcomOfferDesk — полный чек-лист пострелизового тестирования

Дата актуализации: **29.10.2026**, Europe/Moscow. Исходный код: **`without_keycloak_and_others@cb46f68`**. Эта редакция полностью заменяет документ для ветки test. Проверки описаны по текущему коду; на живом стенде они не выполнялись. Все строки журнала имеют исходный статус «Не выполнен».

## 1. Маршруты создания, регистрации, подтверждения и входа

`{APP}` — публичный HTTPS-адрес приложения; `{TOKEN}`, `{CODE}`, `{STATE}`, `{ID}` — фактические значения конкретной проверки. Использовать реальные ссылки, полученные в управляемых тестовых ящиках. Пароли, токены, действующие action/reply/invite-ссылки не сохранять в доказательствах. Аутентификацию обслуживает собственный IAM; бизнес-профиль, оргструктура и область данных хранятся в AcomOfferDesk.

### М01. Начальный суперадминистратор и обычный вход

Получить уже подготовленную тестовую учётную запись суперадминистратора. Публичного создания суперадминистратора нет. Открыть `{APP}/login`: приложение начинает `GET /api/v1/auth/login?next=<local-path>` → IAM `/iam/authorize` → форма `/iam/login` → возврат `/api/v1/auth/callback?code=…&state=…` → защищённая страница приложения. Пароль вводится только на штатной форме IAM. BFF устанавливает HttpOnly access/refresh cookies, клиент загружает `GET /api/v1/auth/session`. JavaScript получает только описание сессии, без access/refresh token.

Прямой `/iam/login` без контекста авторизации должен перезапустить корректный BFF-поток. Обычные `/auth/login` и старый SPA `/auth/callback` совместимы как вход через AuthPage, но не являются регистрацией и не заменяют серверный callback. Стартовая страница выбирается по итоговым permissions: сначала доступный dashboard процесса/экономии/планов, затем `/admin`, `/contractors`, `/requests` либо `/account`. Поэтому экономист и суперадминистратор с dashboard permissions могут стартовать с `/pm-dashboard`, служба безопасности — с `/contractors`. Пользователь `review` или с обязательным профилем направляется в ограниченный кабинет.

Проверки: ENV-01, AUTH-01–AUTH-06, AUTH-11–AUTH-20, IAM-01–IAM-08.

### М02. Создание внутреннего сотрудника

1. Уполномоченный SA/AD/ведущий экономист открывает `/admin` → нужную вкладку → «Создать пользователя». Выбирает допустимую роль, уникальный логин, действительный email и подразделение/узел, если он предлагается формой.
2. `POST /api/v1/users/register` создаёт MAIN-пользователя `active`, IAM-аккаунт `active` без пароля, активную IAM-привязку и неподтверждённый основной email. Для явного `unit_id` проверяются полномочия назначения; без него используется разрешённое размещение создателя. Ведущий создаёт только экономиста, администратор — экономиста/оператора, суперадминистратор — допустимые роли кроме второго суперадминистратора. Контрагента создают отдельным маршрутом.
3. Сохранение сотрудника **не отправляет автоматически письмо задания пароля**. Первый доступ: `/login` → «Забыли пароль?» → `/login?reset=1` → ввод логина или email → `POST /api/v1/auth/password-reset/request`.
4. Если пароля ещё нет, сервис выпускает IAM action `first_access` и отправляет письмо подтверждения через очередь email. Ссылка `/verify-email?token=…` вызывает `GET /api/v1/auth/verify-email`, подтверждает основной email и выдаёт переход на `/api/v1/auth/password/setup?token=…`. Отдельное письмо password_setup отправляется напрямую через SMTP. Проверить и переход из страницы подтверждения, и письмо.
5. На защищённой странице IAM пользователь задаёт пароль. Затем выполняет обычный вход. Если IAM содержит `complete_profile`, открывается `/profile/onboarding` или `/account`; до первого успешного сохранения профиля бизнес-операции закрыты. Сохранение завершает обязательное действие, затем открываются данные по роли и оргструктуре.

Проверки: NEW-01–NEW-12, AUTH-07–AUTH-09, EML-01–EML-12, ORG-01–ORG-05, MODE-01–MODE-12.

### М03. Ручной контрагент и первое самостоятельное использование

Уполномоченный сотрудник открывает создание карточки контрагента → компания, ИНН, телефон, email компании → `POST /api/v1/users/manual-contractor`. Логин генерируется. Создаются MAIN/IAM `active`, связь аккаунта и доступные email-каналы без установленного пароля. Создатель закрепляет контрагента за своей допустимой областью; дубликат должен обрабатываться штатным механизмом поиска/повторного использования.

Для первого самостоятельного входа взять именно сгенерированный логин и фактический primary email: `/login?reset=1` → first_access → подтверждение email → password_setup → обычный вход → complete_profile. Email компании и личный mail профиля сверять отдельно, не предполагать их равенство. Ручное КП новой компании использует тот же проверяемый жизненный цикл, а не отдельного «невидимого» владельца.

Проверки: MAN-01–MAN-08, NEW-03, EML-08, AUTH-07, MODE-02.

### М04. Саморегистрация по персональному приглашению

1. Пользователь с правом приглашения отправляет `POST /api/v1/registration/invitations` с email и допустимым `unit_id`; получает адресат, письмо и срок действия. Ответ API не содержит raw token для ручного распространения.
2. Адресат открывает реальную ссылку `/register?token=…`; frontend проверяет `GET /api/v1/registration/invitations/{token}`. Для действующей ссылки показывается форма: логин, email, ФИО, телефон, компания, ИНН, телефон компании. **Пароль не вводится в этой форме** — он задаётся позже на защищённой странице Acom/IAM.
3. `POST /api/v1/registration/submit` берёт роль и исходный unit-контекст из подписанного приглашения, создаёт MAIN `review`, IAM `pending`, неподтверждённый основной email и запускает first_access. Email формы можно исправить на другой свободный валидный адрес; он должен быть подтверждён. Поле role/unit в пользовательском запросе не даёт произвольно выбрать полномочия.
4. Открывается `/verify-email?next=check_email&invite=…`. Пользователь получает письмо, подтверждает адрес, задаёт пароль по password_setup. Подтверждение и пароль **не переводят review/pending в active**.
5. Уполномоченный SA/AD/служба безопасности проверяет заявку и подтверждает регистрацию. Нужны permission `users.registration.approve` и verified primary email. После одобрения MAIN и IAM становятся `active`.
6. Пользователь входит через `/login` и при необходимости завершает complete_profile. Доступность конкретной закупки проверяется отдельно по привязкам к подразделениям, статусу заявки и скрытию. Само приглашение не гарантирует доступ ко всем заявкам.

Проверки: REG-01, REG-03–REG-12, EML-01–EML-07, USR-01–USR-05, E2E-02.

### М05. Пакет приглашений и приглашение из заявки

В `/contractors` уполномоченный пользователь открывает приглашение контрагентов → список email и обязательный актуальный нормативный материал → `POST /api/v1/contractors/invite`. Проверить `sent`, `failed`, `invalid`, нормализацию/дедупликацию, вложение и контактный блок. Неизвестному адресу выпускается `/register?token=…`. Для уже известного пользователя с IAM-привязкой сервис проверяет наличие пароля и вставляет ссылку `password/setup` (пароля нет) либо `password/reset` (пароль есть). Это не просто портал входа: проверить реальный target письма и неизменность статуса/чужого аккаунта. Без подходящей связи может использоваться настроенный портал. Требуется фактическое permission `users.registration.invite`; наличие одного общего manual-create не должно подменять проверку этого endpoint.

**Дополнительная рассылка заявки отличается:** `SendRequestNotificationEmailUseCase._portal_url_for_invitee` в текущем SHA не выпускает регистрационный token, а возвращает `INVITATION_PORTAL_URL` либо `/login`, даже для неизвестного адреса. Проверить письмо как приглашение в портал; для фактической регистрации нового контрагента затем выпустить отдельное М04 или пакетное приглашение. Скрытие, статус, область и настройки категорий проверяются для известных адресатов. Документ `auth-and-onboarding.md` в части token из additional_emails расходится с кодом; в этом чек-листе приоритет у кода.

Проверки: REG-02, REG-13–REG-16, MAIL-02, MAIL-10, HID-09–HID-12.

### М06. Вход по письму к конкретной заявке

Письмо разрешённому контрагенту → `/login?next=/requests/{ID}/contractor` → BFF `/api/v1/auth/login?next=…` → IAM → BFF callback → исходная карточка. Письмо не создаёт сеанс автоматически. Проверить чистый браузер, активную собственную сессию и вход под другим тестовым аккаунтом. После входа сервер заново проверяет hidden, подразделение, статус пользователя и жизненный цикл заявки. Чужой аккаунт не получает доступ только потому, что у него есть URL.

Проверки: AUTH-03, HID-04–HID-08, E2E-04.

### М07. Подтверждение почты и страницы password setup

Для регистрации/первого доступа используются IAM `first_access`/`verify_email`, для изменения адреса — `profile_change`; одноразовые действия не заменяют статус регистрации. Запрос из профиля: `POST /api/v1/auth/request-email-verification`. Письмо ведёт `/verify-email?token=…`, frontend вызывает `GET /api/v1/auth/verify-email`. Первый доступ возвращает `next_action=password_setup` и локальный `redirect_url`; другой результат может быть `waiting_for_review`, `login` или `first_login`.

Задание пароля выполняется через BFF `GET/POST /api/v1/auth/password/setup?token=…`, восстановление — `/password/reset`. Формы проксируются к IAM по внутренней сети. Проверить одноразовость, срок, назначение токена и отсутствие автоматического одобрения регистрации. Удалять пользователя/подтверждать почту вручную в БД вместо этого маршрута нельзя считать успешным тестом.

Проверки: EML-01–EML-12, AUTH-07–AUTH-09, IAM-07.

### М08. Одобрение регистрации, ограничение и восстановление допуска

SA/AD/служба безопасности открывает `/contractors` или доступную карточку `/admin`, проверяет реквизиты, verified email и оргпривязки → `PATCH /api/v1/contractors/{id}/status` либо разрешённый `/users/{id}/status`. Для `review → active` проверяется отдельное право одобрения. IAM синхронизируется с локальным статусом; сбой IAM не считается успешным локальным изменением.

Письмо «доступ открыт/ограничен» относится к пользовательской категории **system**: при отключённых system-уведомлениях оно может не отправляться. Сам статус и событие в системе при этом должны сохраняться. Это письмо не равно обязательному письму первого доступа. Ограничение `inactive/blacklist` закрывает бизнес-доступ и старые ссылки; восстановление возвращает только разрешённую область.

Проверки: USR-01–USR-10, MODE-04, MODE-05, OPS-02.

### М09. Забытый пароль и отличие от первого доступа

На форме IAM выбрать «Забыли пароль?» → `/login?reset=1` → логин или основной email → `POST /api/v1/auth/password-reset/request`. Ответ нейтральный: «Если учётная запись существует, инструкция отправлена на связанный email». При отсутствии пароля идёт М02 first_access; при уже установленном пароле выпускается `password_reset` и отправляется прямое SMTP-письмо → `/api/v1/auth/password/reset?token=…` → новый пароль → обычный вход.

Успешный нейтральный HTTP-ответ не доказывает существование пользователя или доставку. Перевыпуск, неверный адрес, TTL, повтор ссылки, старый пароль и старые сеансы проверяются отдельно. Сброс пароля не снимает review, blacklist и обязательное заполнение профиля.

Проверки: AUTH-07–AUTH-10, EML-06, MODE-03, MODE-08–MODE-11.

### М10. Незавершённая регистрация и ошибочные ссылки

Без token, с повреждённым/просроченным приглашением или для завершённой регистрации открывается `/auth/registration-link-status?reason=invalid|expired|already_registered`. Пока пользователь `review` и email не подтверждён, inspect может вернуть `in_progress`: форма загружает сохранённые данные и фиксирует исходный логин. Повторный submit корректирует незавершённую заявку и запускает подтверждение по актуальному email, а не создаёт ещё одного человека. После подтверждения/завершения повторная регистрация блокируется.

Для неправильного callback/state IAM используется один безопасный повтор BFF-потока, затем понятная ошибка без бесконечных редиректов. Password/verify-токены разных назначений не взаимозаменяемы.

Проверки: REG-05–REG-10, EML-05–EML-07, AUTH-11–AUTH-12, AUTH-20.

### М11. Существующий пользователь после релиза и выход

Проверить вход прежней IAM-учётной записью, сохранность локального ID, роли, личных grants, unit memberships, КП и истории. JWT sub должен разрешаться в активную IAM-привязку. Исторические записи другого провайдера не дают входа; совпадение логина/email не создаёт неявной связи.

Выход выполняет CSRF-защищённый `POST /api/v1/auth/logout`, затем BFF `POST /iam/acom/logout` для удаления IAM browser cookie. После выхода `/auth/session` недоступен, а новый вход не должен молча восстановить прежнего пользователя через оставшуюся IAM-cookie. Проверить кнопку Back и вторую вкладку.

Проверки: AUTH-13–AUTH-16, OPS-01, OPS-07, IAM-01–IAM-04.

### М12. «Без уведомлений» и физически отключённая почта

`GET/PUT /api/v1/users/me/notification-preferences` управляет пользовательскими категориями `chat`, `request`, `offer`, `system`: режим `email_only` включает их, `none` выключает, разные значения категорий дают `custom`. Режим none не отключает аккаунт, регистрацию, обязательное подтверждение email, first_access и восстановление пароля. Эти письма отправляются отдельными сервисами. Центр уведомлений проверяется независимо от почтовых предпочтений.

**Отключение SMTP/доставки — другой сценарий.** Оно ломает реальную доставку first_access/verify/setup/reset; обхода проверки email и автоматической регистрации без почты нет. Уже активный пользователь с установленным паролем продолжает входить, если IAM доступен. Для QA раздельно проверять очередь/worker (first_access и обычная почта) и прямой SMTP (password setup/reset). После восстановления — допустимый повтор без дублей и без самостоятельного перевода регистрации в active.

Проверки: MODE-01–MODE-12, NTF-01–NTF-06, MAIL-01, MAIL-12–MAIL-14.

## 2. Действующая модель ролей, оргструктуры и индивидуальных прав

В этой ветке **восемь ролей**, полноценные units/grants, нормативный справочник и центр уведомлений. Это реализованный функционал, а не необязательные «целевые» пункты.

| Роль | Основная область проверки |
|---|---|
| Суперадминистратор (1) | Полный закупочный/административный контур; нельзя создать второго SA через обычную форму |
| Администратор (2) | Учётные записи, статусы, назначение разрешённых ролей, оргструктура и индивидуальные доступы |
| Контрагент (3) | Допустимые открытые заявки, собственные КП и чаты, профиль компании |
| Руководитель проекта (4) | Видимость корневого подразделения, распределение, сотрудники, dashboard и личные department-доступы в своей области |
| Ведущий экономист (5) | Закупки и команда своего поддерева, нормативы, приглашения, ручные контрагенты/КП |
| Экономист (6) | Заявки своего unit/subtree и допустимые подчинённые, КП/чаты/планы; соседние ветки требуют расширения |
| Оператор (7) | Собственные заявки до назначения экономиста; до передачи нет contractor discovery |
| Служба безопасности (8) | Контрагенты, проверка допуска, приглашение/одобрение регистрации; закупочных операций по умолчанию нет |

Роль/permissions приходят из проверенного IAM JWT. MAIN role_id не является источником прав. Effective permissions = **права роли UNION индивидуальные grants**; удаления личного grant недостаточно, чтобы отнять право роли. DENY-механизм не предполагается. Изменение личных прав применяется после обновления сессии/нового токена; действие старого токена проверяется в рамках документированного TTL, без обещания мгновенного изменения его claims.

Оргструктура `/admin/hierarchy`: корневое подразделение → вложенные units произвольной глубины → сотрудники. Членство и положение в дереве ограничивают область отдельно от функциональных permissions. РП видит свой корень, ведущий/экономист — своё поддерево; department grants расширяют доступ внутри текущего корневого подразделения. Контрагенты связываются с корнями отдельно, в том числе с несколькими. Справочная старая цепочка руководителей не заменяет unit-memberships; изменение legacy manager не должно давать обход области.

Персональные настройки открываются из карточки сотрудника. `GET/PUT /users/{id}/delegations/department`: просмотр/редактирование/статус/назначение заявок, изменение/принятие/отказ КП, чтение/отправка чатов, dashboard, планы read/manage. SA/AD управляют допустимыми пользователями, РП — другими пользователями своего подразделения; самостоятельно менять свои grants нельзя. `GET/PUT /users/{id}/delegations/contractors`: SA/AD выдают **ведущему экономисту** группу управления статусом контрагентов; она содержит три atomic permissions чтения списка/профиля/изменения статуса. Не придумывать отдельные checkbox upload/delete, отсутствующие в каталоге UI: проверять файлы через конкретные request/offer actions и их реальные permissions.

**[Р]** — проверка по действующему коду/контракту ветки; **[У]** — условная интеграция или согласованный аварийный сценарий. Метка не означает успешное выполнение. Все проверки остаются «Не выполнен» до реального прогона. Статусы: **Не выполнен / PASS / FAIL / BLOCKED / N/A**. Отсутствующая заявленная функция — FAIL; отсутствие стенда/ящика/доступа — BLOCKED с владельцем. N/A допустим только при явном исключении условной интеграции из конфигурации релиза.

## 7. Приоритетные риски по текущему исходному коду

Это статические точки для обязательного прогона, не отчёт о выполненных тестах:

1. Дополнительная рассылка заявки **не выпускает registration token**. В части дополнительных адресов существующая auth-документация расходится с кодом; REG-02 должен проверить фактический portal target. Не считать такой email завершённым приглашением к саморегистрации.
2. Ручная допрассылка передаёт `hidden_contractor_ids=[]`, а `_build_recipients` отдельно фильтрует корни/preferences. HID-11 обязателен: persisted hidden конкретной заявки не должен обходиться повторным email. Не объявлять этот риск устранённым только из-за root-unit фильтра.
3. Пакет существующему IAM-аккаунту создаёт setup/reset action URL и передаёт его в обычный email-service. IAM-07 проверяет соответствие прямому SMTP-контракту secret-bearing писем и отсутствие утечки в broker/logs. При расхождении фиксировать дефект, не маскировать как обычную ссылку входа.
4. First_access идёт через worker, setup/reset — напрямую SMTP. Успех одного пути не доказывает другой; MODE-08/MODE-09 разделяют отказы. Recovery HTTP-ответ остаётся нейтральным даже при недоставке.
5. Mode none выключает категории уведомлений, а не обязательные auth-письма. При отключённом system письмо допуска может отсутствовать без ошибки approval. Проверять фактический status отдельно от письма.
6. Норматив/исходная сумма/собственный файл обязательны в заявке. Скопированный норматив не заменяет пользовательское вложение; презентация письма не равна обязательной копии в карточке.
7. Экономия: отсутствующие данные дают 0; при итог=ТЗ и КП выше ТЗ тоже 0; при КП ниже ТЗ и итог=ТЗ текущая формула даёт отрицательное КП−ТЗ. DASH-04 фиксирует обе ветки без самовольного изменения бизнес-методики.
8. Grants меняют только IAM managed subset и требуют актуализации токена. Источник роли не отзывается снятием личного разрешения; перенос между units всё равно меняет область независимо от набора permission codes.
9. Сохранённая `complete_profile` не имеет короткого TTL. Проверять повторный вход и сохранение профиля, а не ждать, что ограничение само исчезнет. Password setup/verify не заменяют approval.

## 8. Приёмка, smoke и журнал дефектов

Безопасный smoke: ENV-01–ENV-04; NEW-01/NEW-03; AUTH-01/AUTH-03/AUTH-05/AUTH-13/AUTH-16; REG-01/REG-03/REG-11/REG-12/REG-14; EML-01/EML-02; USR-01/USR-04; UNIT-01/UNIT-06/UNIT-12; ACL-03/ACL-05/ACL-06/ACL-17; NOR-07; REQ-01/REQ-12/REQ-19; HID-02/HID-04/HID-06/HID-09/HID-11; OFR-01/OFR-04; CHAT-01; MAIL-01/MAIL-02/MAIL-04; MODE-01/MODE-03/MODE-04; IAM-09. Любой требующий аварии случай выполняется на изолированном стенде и не включается в production-команды.

Полная приёмка требует статуса/evidence всех применимых ID. P0 FAIL, утечка закрытых данных, невозможность регистрации/first_access, потеря файлов/истории, несогласованные роли/статусы MAIN/IAM — блокирующие дефекты. BLOCKED не считается PASS. По P1/P2 необходимы записанные решения владельца релиза; N/A допустим только для явно не настроенной условной интеграции.

Полные action/invite/reply/access/refresh значения и пароли из evidence удалять.

CSV содержит отдельные строки: ID, приоритет, основание, раздел, контекст, действия, ожидание, статус, факт, дефект, evidence, исполнитель, время, SHA стенда. Word содержит колонку результата; Markdown — флажки. Все статусы исходно «Не выполнен». Повтор после исправления фиксируется новым временем/SHA с сохранением связи с исходным дефектом. Автоматический перенос PASS из документа старой ветки запрещён.
