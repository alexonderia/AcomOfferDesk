# Техническое задание: импорт сотрудников и создание юнитов

Версия 1.1 · 03.11.2026 · AcomOfferDesk · исправлено по системным ролям

## 1. Цель и результат

Внести в AcomOfferDesk всех 45 сотрудников из файла «Организационная структура сотрудников итог.xlsx», лист «Оргструктура», и создать для каждого отдельный активный персональный юнит. Выстроить дерево подчинённости, назначить системные роли, все штатные права этих ролей и индивидуальные готовые пароли.

Способ выполнения: контролируемое прямое заполнение основной БД (MAIN) и БД IAM. Регистрация, приглашения, письма, подтверждение email, first_access, password_setup и обязательное заполнение профиля при первом входе не используются. IAM сохраняется как сервис проверки пароля, выдачи токенов и сессий. Отдельный локальный механизм входа не требуется.

Настоящий документ — ТЗ на последующую реализацию. При подготовке ТЗ подключений к БД, создания пользователей, генерации действующих паролей и изменения кода приложения не выполнялось.

## 2. Подтверждённые решения заказчика

- Елышева Наталья Владимировна (Ст.СПЕЦ) подчиняется непосредственно Плеховой Виктории Александровне. Для неё создаётся отдельный юнит; системная роль — «Экономист».

- Прямое создание строк выполняется в обеих БД; IAM остаётся для входа. Обход относится к регистрации и активации, а не к проверке подлинности пользователя.

- Каждому сотруднику выдаётся отдельный готовый пароль. Схема «пароль равен логину» не применяется.

- Хлистун Владислав Станиславович получает полный доступ к подразделению под Ермошкиным. Его непосредственный руководитель — Яруллин; системная роль остаётся «Ведущий экономист». Полный доступ действует внутри подразделения и в рамках допустимых операций, без выдачи роли администратора или суперадминистратора.

## 3. Источник и правила сопоставления

Источник содержит ФИО, организационный уровень, роль и примечание. Логинов, email, телефонов, идентификаторов сотрудников и паролей в нём нет. Имена нормализовать только по пробелам, сохраняя буквы, включая «ё», и исходное написание. Не исправлять ФИО по предположению.

Ключи S002–S050 в приложениях обозначают строку исходного Excel и служат для сверки этой поставки; это не значения production ID и не универсальные кадровые идентификаторы. Сотрудники и юниты привязываются через постоянный манифест импорта с UUID/ID фактически созданных объектов.

До записи сформировать таблицу соответствий «ФИО → существующий либо новый логин → MAIN users.id → IAM accounts.id → units.id». Проверить совпадения с существующими сотрудниками. Одного совпадения ФИО недостаточно для автоматического объединения. Конфликт логина, роли, принадлежности или неактивной учётной записи включить в отчёт и не устранять скрытым перезаписыванием.

Для новых пользователей предлагается логин вида латинская_фамилия.имя; коллизии разрешать стабильным суффиксом, зафиксированным в манифесте. Это проектное правило, а не данные Excel. Существующие согласованные логины сохранять. Итоговые логины согласовать в реестре до выполнения импорта. Email и телефон при отсутствии данных оставлять NULL; фиктивные адреса и признаки подтверждения не создавать.

## 4. Иерархия по системным ролям и контрольные количества

Основная цепочка системных ролей: РП → ВЭ → ВЭ → Экономист → Экономист. Повторяющиеся роли допустимы на разных ступенях. Уровни исходного Excel (МРП, ВС, СПЕЦ, Ст.СПЕЦ, МС) определяют только порядок подчинения сотрудников и не являются ролями системы или отдельными типами юнитов.

Ермошкин — РП; под ним четыре ВЭ: Миннебаева, Плехова, Хабибулин и Яруллин. Под ними находятся соответствующие ВЭ следующей ступени; далее — экономисты и подчинённые им экономисты. Елышева — экономист, напрямую под ВЭ Плеховой. Все связи указаны персонально в приложении А; перестановка по величине role_id недопустима.

На каждую строку сотрудника создать или переиспользовать один персональный юнит с именем «<системная роль> — <полное ФИО>». Например, «Ведущий экономист — Миннебаева Гульгена Наилевна» и «Ведущий экономист — Белунькин Дмитрий Юрьевич»: роль одна, а юниты расположены на разных ступенях. units.id_parent указывает на персональный юнит непосредственного руководителя. Юнит Ермошкина — корень данной поставки (id_parent=NULL); не присоединять его к другой структуре по предположению.

Каждого сотрудника включить только в собственный персональный юнит одной активной строкой unit_members. Руководителей не дублировать в юнитах потомков; доступ определяется деревом и политиками. Наличие персональных юнитов МС необходимо, даже если у них нет подчинённых.

Контроль: 45 сотрудников; 45 юнитов в целевой структуре; 45 основных активных членств; 44 связи родитель–потомок; один корень; циклов нет. При повторном запуске эти числа обозначают итоговую структуру, а не обязательное количество новых INSERT.

По уровням: РП — 1; МРП — 4; ВС — 11; СПЕЦ — 19; Ст.СПЕЦ — 1; МС — 9. По ролям: project_manager — 1; lead_economist — 15; economist — 29. Ветки с учётом самого МРП: Миннебаева — 14, Плехова — 7, Хабибулин — 13, Яруллин — 10; плюс Ермошкин — 1.

## 5. Системные роли и функциональные права

Организационный уровень и системная роль — разные сущности. РП получает MAIN id_role=4 / IAM role name project_manager; МРП и ВС — MAIN id_role=5 / IAM lead_economist; СПЕЦ, Ст.СПЕЦ и МС — MAIN id_role=6 / IAM economist. Роли «МРП», «ВС», «СПЕЦ», «МС» в IAM не создавать. Числовые IAM role_id разрешать по roles.name, не копировать числовой ID из MAIN.

Каждому сотруднику выдать полный штатный набор функциональных permissions своей роли. Приложение В содержит снимок набора из backend/app/domain/permissions.py текущей рабочей копии. Перед выполнением сверить его с фактическими IAM roles, permissions и role_permissions; расхождения явно включить в dry-run. Общую матрицу ролей ради одной поставки не расширять.

Эффективные права поступают из проверенного IAM JWT. Одного users.id_role недостаточно. Backend дополнительно применяет статус пользователя, область юнитов и ограничения операций; интерфейс использует permissions/actions. Наличие права на операцию не даёт доступ к любому объекту системы.

Области данных рассчитываются по вложенности юнитов и политике конкретного действия: собственный юнит, допустимые потомки, справочная видимость руководителей, полномочия РП на подразделение. Для ВЭ → ВЭ устранить несогласованность, описанную в разделе 10. Проверять каждую операцию на API. Не заменять область доступа общей выдачей admin/superadmin.

## 6. Полный доступ Хлистуна к подразделению Ермошкина

Хлистун получает базовую роль lead_economist и индивидуальные grants на все 15 известных department.* permissions: заявки — чтение, изменение, статус, назначение; КП — изменение, принятие, отклонение; чаты — чтение и отправка; файлы — чтение, загрузка, удаление; статистика — чтение; планы — чтение и управление.

Grants создаются непосредственно в IAM account_permission_grants через реальные permissions.id. Точный список — в приложении В и permissions-snapshot.json. Эти права назначаются только Хлистуну, без изменения общей роли ведущего экономиста.

Область — весь корневой юнит Ермошкина и его потомки, включая все четыре ветки МРП, все 45 сотрудников этой поставки и существующие объекты подразделения, относящиеся к этому дереву. Доступ должен покрывать реестры сотрудников, дерево, заявки, КП, чаты, файлы, дашборды и планы в пределах разрешённых бизнес-операций.

Хлистуна не включать дополнительно в корень или в чужие персональные юниты: расширение предоставляется правами и областью данных. Подчинённость остаётся Яруллин → Хлистун. Повышение роли, выдача прав на чужие подразделения и административное управление IAM не входят в понятие полного доступа к подразделению.

Управление ролями, статусами и учётными записями выполняется в пределах штатного потолка ВЭ. Структурное подчинение и функциональная делегация не дают права менять РП или произвольно повышать других ВЭ. Если конкретный API игнорирует индивидуальный department grant, это дефект реализации области, который необходимо исправить и проверить, а не обходить дополнительным членством или повышением роли.

## 7. Записи основной БД (MAIN)

- users: стабильный согласованный id/логин, id_role по таблице ролей, конечный status=active. users.id_parent при заполнении дублирует непосредственного руководителя только для справки; источником бизнес-доступа он не является.

- profiles: id=users.id, полное ФИО из реестра; mail/phone=NULL, если реальные данные не предоставлены. Профиль заполнен настолько, насколько это необходимо для рабочего входа; почтовый onboarding не назначается.

- units: по одному юниту на сотрудника, корректный id_parent, is_active=true; служебные даты и инициатор по принятому контракту. unit_members: связь собственного юнита и users.id, is_active=true, корректный инициатор назначения.

- user_auth_accounts: id_user=users.id, provider='iam', external_subject_id=строковый UUID соответствующего IAM accounts.id, external_username=согласованный логин, is_active=true. Не использовать исторические provider как альтернативный вход.

- Не писать открытые пароли или хеши в profiles, users, примечания, контактные каналы или манифест с несекретной структурой. В основной схеме отсутствует штатное поле пароля.

- Не создавать пустые/фиктивные строки user_contact_channels и не проставлять is_verified=true без факта подтверждения. Предпочтения уведомлений создавать только при наличии реального канала и необходимости по контракту.

## 8. Записи IAM и готовые пароли

accounts: UUID, согласованный уникальный login, role_id найден по техническому имени роли, конечный auth_status=active, required_actions=[]. UUID и логин должны точно совпадать со связью в MAIN; использовать стабильный UUID в манифесте либо штатный алгоритм stable_iam_account_id. При повторе сохранять исходный UUID.

account_credentials: одна строка на accounts.id; password_hash — индивидуальный валидный Argon2id-хеш; password_algo='argon2id'; password_changed_at заполнен; для нового аккаунта failed_login_count=0, locked_until=NULL. Хеш генерируется той же реализацией и параметрами, что iam/iam_app/core/security.py; работоспособность проверяется verify_password, а не сравнением текстов хеша.

На этапе импорта сгенерировать каждому новому сотруднику уникальный готовый пароль длиной 16 символов, с буквами разных регистров, цифрами и допустимыми специальными символами, совместимый с текущей политикой 12–128 символов. Конкретные пароли в это ТЗ не включаются. Перечень «ФИО — логин — пароль» передаётся уполномоченному получателю отдельным закрытым файлом и не попадает в репозиторий, логи SQL, отчёт dry-run или общую картинку.

Пароль сразу рабочий: обязательные password_setup, first_access, complete_profile, подтверждение email и согласование review не требуются. Самостоятельная смена известного пароля в профиле остаётся доступна штатным способом без почты.

account_permission_grants: индивидуальные department grants Хлистуна. Для остальных — штатная матрица роли без случайных индивидуальных расширений. Существующие согласованные права не удалять без явного отражения в плане изменений.

Не создавать auth_sessions, authorization_codes или почтовые action tokens за пользователя. Сессия и код авторизации появляются при реальном входе. Не подделывать существующие события auth_audit_log: учёт прямой загрузки вести отдельным служебным журналом; штатный аудит входа формирует IAM.

Повтор импорта не генерирует новый пароль, не меняет уже сменённый пользователем пароль и не снимает блокировку. Существующий активный пользователь переиспользуется только после сверки identity; заблокированный/неактивный аккаунт — отдельный конфликт для решения, а не автоматическая активация.

## 9. Завершённость маршрутов регистрации и активации

Требуемая цепочка входа: /login → /api/v1/auth/login → /iam/authorize → /iam/login → /api/v1/auth/callback → рабочая область. После входа /api/v1/auth/session должен возвращать правильные user_id, role_id, permissions, status=active, business_access=true и отсутствие незавершённого onboarding.

При импорте не вызывать /api/v1/users/register, выдачу приглашений, регистрацию по ссылке, отправку подтверждения email, recovery, first_access или password_setup. Строки БД формируют уже завершённое состояние; обязательный переход на эти экраны при первом входе отсутствует.

Не создавать фиктивные использованные токены и не отмечать чужой email подтверждённым. Не отключать глобально маршруты /auth/login, /auth/callback, /auth/session, /auth/refresh, /auth/logout: они необходимы для входа через IAM.

Под «закрытием маршрутов» для этой поставки понимается отсутствие незавершённых этапов onboarding у импортируемых сотрудников, а не удаление API во всей системе. Глобальное отключение почты или запрет регистрации другим пользователям в объём импорта не входит. Сам импорт не публикует почтовые события и не отправляет SMTP-письма при любом значении EMAIL_ENABLED.

## 10. Связь ВЭ → ВЭ: ограничение и способ реализации

Ограничения на саму запись дерева ВЭ → ВЭ нет: units.id_parent ссылается на юнит и не сравнивает роли его участников. UnitService.create_unit проверяет права инициатора и доступ к родительскому юниту, но не запрещает одинаковые роли на соседних ступенях. Более того, users.py::_hierarchy_rule_for_role прямо допускает ВЭ в качестве руководителя пользователя с ролью ВЭ.

Несогласованность возникает при расчёте персональных руководителей и подчинённых: UnitHierarchyService._can_manage вызывает UserPolicy.can_manage_subordinate_role. Последняя возвращает false для ВЭ → ВЭ, разрешая ВЭ только цели «Экономист» и «Оператор». Этот фильтр используется в get_user_managers/get_user_subordinates, от которых зависят is_manager_of и часть проверок управления сотрудником. Поэтому ограничение затрагивает не только отображение подписи руководителя.

Частичный обход без изменения приложения: создать вложенные юниты и членства напрямую в БД либо от имени пользователя с достаточными правами. Дерево сохранится; вычисления видимости по самому поддереву могут учитывать его. Однако это не устраняет фильтр персональных руководителей, проверку is_manager_of и отдельные ограничения управления профилем. Такой результат не считается полной реализацией ТЗ.

Требуемое решение при реализации: организационное отношение определять по активным персональным юнитам и строгому пути предок → потомок, независимо от совпадения системной роли. Непосредственный руководитель — участник ближайшего подходящего юнита-предка. Не сортировать кандидатов только по ID роли или ФИО: такая сортировка не определяет ближайшего руководителя. Разделить структурное отношение и разрешение конкретного действия.

Операция над подчинённым должна требовать штатный permission действия, действующее структурное подчинение в своей ветке и соблюдение специфических ограничений операции. Для управления профилем ВЭ-потомка проверить также UserQueryService._ensure_accessible_subordinate: он отдельно вызывает ту же ролевую проверку. Не оставлять второй запрет после исправления вычисления дерева. Смена системной роли и выдача индивидуальных прав продолжают подчиняться отдельным потолкам доступа.

Для равных ролей связь в одном юните не устанавливает старшинство: использовать разные вложенные юниты. Обратная связь, самоподчинение, цикл и управление соседней веткой запрещены. Не добавлять ВЭ в общий список разрешённых целей без проверки вложенности и всех мест использования helper; изменение одной строки может расширить права за пределы требуемого отношения.

Приёмка исправления: Миннебаева (ВЭ) признаётся непосредственным руководителем Белунькина (ВЭ); Белунькин не признаётся руководителем Миннебаевой; Крамской (ВЭ) не получает управление Белунькиным из соседней ветки. Экономист СПЕЦ → экономист МС также определяется по юнитам. Дополнительные grants IAM, users.id_parent и искусственное повышение роли не заменяют исправление структурной проверки.

Стандартная область department определяется корневым юнитом. Для Хлистуна это соответствует подтверждённому подразделению Ермошкина. Все модули должны одинаково учитывать это расширение; department grants не являются основанием менять непосредственного руководителя.

В перечне department permissions есть файловые read/upload/delete, которых нет в старом UI-списке department delegation. Поэтому ограничиться историческими delegation.* кодами недостаточно: использовать реальные IAM permissions, проверенные backend, и отдельно проверить действия с файлами и чатами.

Снимок ТЗ получен по рабочей копии ветки dev от 03.11.2026 с ранее существовавшими незакоммиченными изменениями. Перед выполнением зафиксировать целевой релиз, актуальные версии миграций MAIN/IAM и полный dry-run. Данные реальной БД при подготовке ТЗ не исследовались.

## 11. Порядок выполнения и повторяемость

- 1) Зафиксировать целевое окружение/релиз, снимки обеих БД и версии схем. Выполнить проверку без записи: реестр, роли, права, свободные логины, существующие identities, конфликтующие юниты и членства.

- 2) Сохранить постоянный манифест: import_id, checksum Excel, ключи строк, логины, MAIN user ID, IAM UUID, unit ID, роль, родитель, признак created/reused, фазы выполнения. Пароли хранить отдельно; в манифесте допустима только защищённая ссылка на их передачу.

- 3) Учитывать, что MAIN и IAM могут быть отдельными БД: обычного BEGIN/COMMIT на одной связи недостаточно для атомарности обеих. Использовать фазовую запись с повторным запуском и компенсацией. Не объявлять успех после записи только одной стороны.

- 4) Новые IAM accounts подготовить в неактивном для входа состоянии disabled с credentials и grants; новые MAIN users — inactive с профилями, юнитами и bindings. Записать дерево сверху вниз; проверить все 45 связей перед активацией. Для уже существующих активных аккаунтов использовать отдельный план без массового отключения.

- 5) После сверки обеих сторон активировать IAM accounts, затем MAIN users; при ошибке оставить неполную новую identity недоступной и завершить фазу повтором или компенсацией. Выдавать пароли и объявлять готовность только после конечной проверки.

- 6) Выполнить проверку фактических структурных связей, JWT permissions, регионов видимости и входа. Для ранее вошедших пользователей обновить сессию, чтобы индивидуальные grants появились в новых токенах.

- 7) Повтор с тем же import_id и манифестом не создаёт пользователей, юниты, credentials, grants и memberships повторно. Не полагаться только на UNIQUE(id_parent,name): у корневых строк NULL может допускать дубли. Корень и стабильные identity проверять явно.

- 8) Итоговый отчёт: создано/переиспользовано/изменено/конфликты, контрольные количества, UUID/ID, результат входа и тестов, точное число индивидуальных grants; никаких паролей и хешей.

## 12. Приёмка

- Реестр: все 45 ФИО исходника представлены ровно один раз. 45 целевых юнитов, 45 основных активных членств, 44 родительские связи, 1 корень; по веткам 14/7/13/10 + РП. Каждый parent_key совпадает с приложением А и изображением.

- Исключение: у Елышевой parent unit — Плехова, роль economist. У Хлистуна parent unit — Яруллин, роль lead_economist; нет дополнительных членств в корне или соседних ветках.

- Каждой из 45 identities соответствуют активные users/profiles/binding/accounts/credentials и согласованные логины/UUID/роли. Существующие пароли при повторе сохранены. Для новых паролей проверено успешное verify_password без вывода секрета.

- Фактический вход проверен для РП, МРП, ВС, СПЕЦ, Ст.СПЕЦ, МС и отдельно Хлистуна. Нет писем, обязательной смены/установки пароля, complete_profile, ожидания одобрения или зависимости от SMTP. Неверный пароль не создаёт сессию; refresh/logout и смена собственного пароля работают.

- Роли и действия: итоговый набор штатных permissions совпадает с согласованной матрицей, дополнительные department grants есть только у Хлистуна. UI и API показывают доступные действия согласованно; недоступная операция отклоняется сервером.

- Оргструктура: в дереве и профиле каждого ВС непосредственным руководителем отображается соответствующий МРП, несмотря на одинаковую роль ВЭ. У МС руководитель — его СПЕЦ; должности и ФИО не подменяются.

- Хлистун: проверены просмотр сотрудников и рабочих объектов, изменение заявки/статуса/назначения, изменение/принятие/отклонение КП, чтение/отправка в чат, чтение/загрузка/удаление файла, просмотр статистики и управление планами на объектах в разных ветках всех четырёх МРП. Ограничения статуса бизнес-объекта продолжают действовать.

- Изоляция: экономист, обычный ВС и МРП не получают новых полномочий на соседние ветки сверх штатной матрицы; Хлистун не получает доступ к другому корню и административным функциям. Отдельно проверять чтение и изменение прямыми API-запросами.

- Повторный запуск создаёт 0 новых пользователей, 0 новых юнитов, 0 новых членств и 0 лишних grants; исходные UUID, логины и пароли не изменяются. Имитированная ошибка между БД не оставляет доступную неполную identity.

- Почтовые действия импорта отсутствуют в событиях/очередях; существующие пользователи и другие подразделения не затронуты. Закрытый файл реквизитов передан отдельно, итоговый несекретный отчёт сохранён.

## 13. Откат

До выполнения иметь проверенные резервные копии обеих БД и манифест созданных/переиспользованных строк. Для отмены отозвать новые сессии затронутых identities, заблокировать вход новых аккаунтов и деактивировать относящиеся к поставке новые связи/юниты. Переиспользованные записи не удалять.

Восстановление прежних ролей, grants, родителей и статусов выполнять по сохранённым значениям только для изменённых записей. После появления бизнес-объектов физическое удаление пользователей недопустимо без проверки ссылок; использовать деактивацию. Откат обеих БД должен быть согласован, зарегистрирован в журнале и проверен повторным входом/запретом входа.
