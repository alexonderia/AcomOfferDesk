# Работа без почтового сервиса

## Включение режима

Установить `EMAIL_ENABLED=false` в env-файле, переданном Compose через `--env-file`. Общий runtime env приложения задаётся через `APP_RUNTIME_ENV_FILE`; рекомендуется использовать один файл для обеих целей. Compose требует явный непустой флаг и передаёт его через общий `environment` в **backend и notifications_worker**, поэтому этот флаг имеет приоритет над значением внутри runtime env. Проверить `config --quiet`, затем пересоздать оба сервиса с одной конфигурацией; простой `restart` новые env-значения не применяет. При обновлении backend выполнить штатное обновление gateway. IAM продолжает работать со своими настройками. Интерфейсу отдельный build-time флаг не нужен.

При `false` не требуются `EMAIL_ADDRESS`, `EMAIL_APP_PASSWORD`, `SMTP_HOST`, `EMAIL_VERIFICATION_SECRET`. IAM, PostgreSQL, MinIO и RabbitMQ по-прежнему нужны для соответствующих функций приложения.

Шаблоны окружений задают `false`; Compose без явного значения не запускается. При запуске приложения вне Compose программное значение по умолчанию остаётся `true`. Сбой SMTP сам по себе режим не переключает. Для возврата к `true` заполнить почтовые настройки и пересоздать оба сервиса. Ранее созданные готовые аккаунты сохраняют пароли и статус.

Для существующего локального dev-стека:

```powershell
docker compose --env-file .env.dev -f docker-compose.yml -f docker-compose.dev.yml config --quiet
docker compose --env-file .env.dev -f docker-compose.yml -f docker-compose.dev.yml up -d --no-deps --force-recreate --wait backend notifications_worker
docker compose --env-file .env.dev -f docker-compose.yml -f docker-compose.dev.yml exec -T gateway nginx -s reload
```

После готовности сервисов `GET /api/v1/auth/capabilities` должен вернуть `email_enabled=false` и `direct_user_creation=true`. Открытые браузерные сессии получают режим при обновлении session DTO; страницу можно перезагрузить.

## Поведение

- UI получает `email_enabled`, `direct_user_creation`, `password_change` из `GET /api/v1/auth/capabilities`; признак почтового режима также входит в session DTO.
- Обычные сообщения не публикуются для почтовой отправки, секретные ссылки не отправляются напрямую через SMTP, IMAP polling не запускается. Worker не потребляет очередь почты. Уже накопленная очередь сохраняется и может быть обработана после включения почты.
- Явные почтовые действия (recovery, запрос подтверждения, новые приглашения, рассылка заявки) возвращают объяснение недоступности. Новые токены/вложения для отключённого действия не готовятся. Существующие ссылки обрабатываются по прежним правилам срока действия.
- Внутренние уведомления, realtime, чат и бизнес-операции сохраняются. Настройки уведомлений показывают недоступность email, сохраняя прежние настройки до повторного включения сервиса.
- Режим не подтверждает email автоматически и не меняет требования одобрения существующей саморегистрации `review`.

## Создание пользователя

В администрировании выбрать допустимую роль и подразделение, указать логин, начальный пароль и повтор. Email необязателен. Новый пароль — **12–128 символов**, пробелы значимы. Права создания и область проверяет backend.

`POST /api/v1/users/register` принимает `password` и `password_confirmation` только при отключённой почте. IAM хранит Argon2-хеш; бизнес-БД пароль не получает. Новый аккаунт готов к входу без обязательного письма и `complete_profile`. Источник выдачи доступа записывается в IAM-аудит.

В форме ручного контрагента поля доступа необязательны: их заполняют вместе, если нужен вход. Справочную карточку для ручного КП можно создать без пароля. Переиспользование существующей компании не выдаёт права на инициализацию её credentials. Для такой записи требуется отдельное штатное восстановление доступа, когда оно доступно; смена собственного пароля требует уже известного текущего пароля.

Независимо от места создания (справочник или ручное КП в заявке), новый контрагент
получает IAM account и активную IAM-привязку. Без начального пароля индикатор
показывает «Пароль не задан». «Не выдан» остаётся возможным для исторических записей
без IAM-привязки. Проверка индикатора сама не синхронизирует данные.

При создании нового контрагента в справочнике начальные логин и пароль может задать пользователь с `contractors.manual.create` в своей области доступа. В штатной матрице это суперадминистратор, администратор, руководитель проекта, ведущий экономист и экономист. Для уже существующего аккаунта повтор создания не является способом установить или заменить пароль: используется отдельный административный сброс, описанный ниже.

В списке и карточке контрагентов «Вход в личный кабинет» проверяется отдельно от
бизнес-статуса «Активен». Система учитывает активную IAM-привязку, совпадение
identity, статус учётной записи и роли, наличие пароля, временную блокировку
после неудачных попыток и необходимость заполнить профиль. Показываются состояния
«Вход доступен», «Не выдан», «Вход отключён», «Ожидает активации», «Пароль не задан»,
«Нужно заполнить профиль», «Временно заблокирован» и «Не удалось проверить».
Последнее не означает отсутствия доступа.
У каждого статуса есть пояснение при наведении и фокусе с клавиатуры;
на сенсорном экране оно открывается удержанием статуса.
В таблице и мобильных карточках вкладки «Контрагенты» состояние входа показано
иконкой рядом с бизнес-статусом, без отдельной колонки. Подсказка содержит
название состояния и пояснение. В подробной карточке сохраняется текстовый индикатор.
В карточке кнопка «Проверить доступ»
обновляет результат; автоматического опроса нет. Проверка не выдаёт доступ,
не создаёт учётные записи и не меняет пароли.

Тот же индикатор отображается в данных контрагента в заявке (таблица и мобильная
карточка КП) и в рабочем пространстве КП при `actions.view_contractor_info`.
Контрагент в собственном КП также получает проверенный сервером индикатор своего аккаунта; совпадение логина с текущей сессией не отменяет запрос. Проверять чужие аккаунты это не позволяет.
При открытии чата состояние проверяется повторно. Для `not_granted`, `blocked`,
`pending`, `password_not_set` и `temporarily_locked` чат предупреждает о
недоступности входа значком рядом с кнопкой отправки. Причина показывается
в подсказке при наведении, фокусе с клавиатуры или удержании на телефоне;
верхнего текстового блока нет. `setup_required` означает, что вход возможен,
но нужно завершить профиль, поэтому предупреждения об отсутствии доступа нет.
При `unknown` показывается информационный значок с подсказкой о неудачной проверке.
Предупреждение не меняет серверные права отправки сообщений. Повторная проверка
доступна только во вкладке «Контрагенты»; в заявке, КП и чате кнопок ручной проверки нет. Загрузка и ошибка
не превращаются в подтверждённый отказ во входе.

`GET /api/v1/contractors/login-access?contractor_id=LOGIN` принимает до 100
контрагентов и возвращает только код состояния, русские label/description и
логин контрагента. Требуется `contractors.read`, `users.read` либо
`offers.contractor_info.read` для сведений в заявке/КП;
для каждой записи сервер проверяет область подразделений и ограничения identity.
IAM-проверки выполняются с ограничением параллелизма. При недоступности IAM список
остаётся доступным, состояние входа отображается как непроверенное.

При обновлении сначала применить IAM с расширенными метаданными внутреннего
`credential-state`, затем backend и web. На прежнем IAM без признака активности
роли backend не подтверждает доступ и возвращает «Не удалось проверить».

Повтор создания не сбрасывает пароль и не снимает блокировку. IAM допускает повтор прямого создания только для той же identity, созданной этим способом, с совпадающими логином, ролью и действующим паролем. После смены пароля старые реквизиты создания повторять нельзя.

## Самостоятельная смена пароля

Открыть **«Профиль» → «Изменение пароля»**, указать текущий пароль, новый и повтор нового, нажать **«Сохранить пароль»**. Форма находится внутри профиля, включая профиль СА; отдельной кнопки в навигации и дополнительного окна нет. При закрытии профиля введённые пароли очищаются. Операция работает и с включённой почтой.

У каждого парольного поля есть кнопка «глаз»: она показывает или скрывает только это поле, не отправляя форму и не меняя значение. По умолчанию пароли скрыты. Переключатель также доступен при задании пароля сотруднику/контрагенту; на странице входа он уже предусмотрен.

`POST /api/v1/users/me/password` берёт account/session ID из авторизации. IAM проверяет принадлежность и состояние сессии и текущий пароль. При неверном пароле данные не меняются. Применяются CSRF и ограничение частоты; секреты исключены из ответов валидации и аудита.

После успеха IAM отзывает refresh-сессии и незавершённые setup/reset-токены, cookie текущего клиента очищаются, необходим новый вход. IAM browser session тоже становится недействительной. Выданные access JWT других клиентов действуют до `exp` (по умолчанию 300 секунд); локальная проверка backend не выполняет онлайн-интроспекцию каждой сессии.

## Миграция и данные

Перед запуском новой версии backend применить `V1.0.8__qa_feedback_and_chat_unit_scope.sql` основной БД: новые поля обратной связи, provider `iam`, синхронизация участников чата по units и пересчёт существующих чатов. Новых IAM-миграций нет.

Миграция добавлена в локальный источник `../order_database/flyway/sql` и идентичный снимок `deploy/order_database/flyway/sql`. Исторические наборы миграций этих репозиториев различались до изменения. Перед выпуском сверить Flyway `info` и `validate` с историей **конкретной БД**; старые миграции/checksums автоматически не заменять и `repair` для подавления расхождения не запускать. Применение и восстановление выполняются по [runbook БД](order-database-vps.md) с резервной копией. Проверить новую функцию на копии PostgreSQL до выпуска.

Отчёт без изменения данных:

```powershell
docker exec backend python -m app.scripts.audit_qa_state --check-iam --check-storage
```

Отчёт содержит логины, состояния IAM и доступность нормативов; хранить как служебные данные. Отсутствие binding видно и без `--check-iam`. Проверка файлов использует stat без скачивания содержимого. Недоступность сервиса отличается от отсутствия содержимого.

После проверки отчёта можно восстановить **конкретную** IAM-связь:

```powershell
docker exec backend python -m app.scripts.audit_qa_state --user LOGIN --check-iam --repair-bindings
```

Команда сверяет существующий IAM subject и точный логин, не создаёт аккаунты и не меняет пароли. При отсутствии IAM account возвращается ошибка для отдельного восстановления. Та же проверка используется API роли/статуса при отсутствии активной связи. Норматив без содержимого нужно загрузить повторно из достоверного источника; отчёт его не восстанавливает.

## Синхронизация исторического пользователя

Для существующей локальной записи без IAM account используется точечная команда.
Сначала выполнить проверку без изменений:

```powershell
docker exec backend python -m app.scripts.sync_user_iam --user LOGIN
```

После проверки и разрешения на изменение конкретной записи:

```powershell
docker exec backend python -m app.scripts.sync_user_iam --user LOGIN --apply
```

Команда создаёт отсутствующие IAM account и связь с точным локальным логином и
ролью. Email и пароль не требуются. Бизнес-статус, подразделения и КП сохраняются.
Повтор не меняет пароль, существующий IAM-статус, required actions и не активирует
отключённую привязку. При несовпадении identity/роли либо чужом subject выполнение
останавливается с ошибкой. Это синхронизация identity; готовность к входу по-прежнему
определяется наличием пароля и состоянием доступа.

## Административный сброс пароля пользователя

В администрировании открыть карточку сотрудника или контрагента → **Сбросить пароль**. Указать новый пароль и повтор (12–128 символов). Старый пароль пользователя не требуется. Суперадминистратор может сбрасывать пароли глобально, администратор — только пользователям своего подразделения, включая вложенные объединения. Используется существующая область `DepartmentScopeService` по активным units/memberships; без привязки к подразделению действие недоступно. Инициатор должен иметь проверенное IAM-разрешение `users.password.update`; другие роли не получают это действие через индивидуальный grant. Сброс паролей любых суперадминистраторов и собственного аккаунта запрещён. Собственный пароль меняется в профиле с проверкой текущего.

Для активного контрагента с IAM-связью и индикатором **«Пароль не задан»** это же действие устанавливает первый пароль. После сохранения нажать **«Проверить доступ»** в карточке и передать контрагенту адрес приложения, его логин из карточки и заданный пароль. Кнопка проверки сама доступ не выдаёт; при статусе `review` или блокировке установка пароля не заменяет одобрение или разблокировку.

`POST /api/v1/users/{user_id}/password/reset` принимает `new_password` и `password_confirmation`, возвращает пустой `204`. Backend повторно вычисляет область подразделения, проверяет роль инициатора и цель, активную IAM-связь, точное совпадение логина и роли. Списки сотрудников и контрагентов возвращают `actions.can_reset_password`; отсутствующий/ложный флаг скрывает кнопку. Видимость карточки или контрагента сама по себе не даёт право сброса.

IAM повторно проверяет действующую сессию, актуальную роль (`superadmin`/`admin`) и эффективное разрешение инициатора, защищает учётные записи суперадминистраторов. Для роли `admin` private API дополнительно требует `department_scope_verified=true`, которое передаёт только доверенный backend после проверки подразделения; значение из публичного запроса пользователя не используется. Оргструктура остаётся в Acom. Аудит `password.administratively_reset` включает `authorization_scope=department|global`. Rollout: сначала IAM, затем backend, затем web; новых permissions и миграций не требуется.

Работает при включённой и отключённой почте. Письма не отправляются. Логин, роли, блокировка/одобрение пользователя и требование заполнить профиль сохраняются; сброс не выдаёт доступ заблокированному или ожидающему одобрения пользователю. При отсутствии активной IAM-связи сначала требуется её восстановление.

Новый пароль хешируется Argon2id; счётчик ошибок входа и временная блокировка пароля очищаются. Прежние refresh-сессии, браузерный вход IAM, незавершённые коды входа и ссылки настройки/восстановления пароля отзываются. Уже выданный access JWT действует до истечения своего TTL (по умолчанию 300 секунд); мгновенное прекращение всех API-запросов по старому JWT не гарантируется. Событие `password.administratively_reset` содержит инициатора и цель без пароля. Новый пароль передаёт пользователю сам суперадминистратор.
