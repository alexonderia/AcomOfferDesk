# Спецификация из договора

## План реализации

1. Реализовать локальный разбор DOCX, XLSX, PDF и сканов PDF/PNG/JPEG в backend.
2. Создавать новый DOCX только из разрешённых полей позиций, без цен и реквизитов.
3. Показывать спецификацию и закрытые исходники в существующем подтверждении заявки.
4. Связывать скрытые исходники с заявкой отдельно от публичных вложений. Разрешать чтение
   всем внутренним пользователям с доступом к конкретной заявке, запрещать контрагентам.
5. Проверить извлечение, подмену файлов, скачивание, письма и frontend.

## Контракт

Исходники проходят `file_guard` до обработки. Подготовка не сохраняет данные в БД
или MinIO. Сервер подписывает контрольные суммы исходников и готовой спецификации,
идентификатор пользователя и срок действия. При подтверждении backend проверяет
подпись и сохраняет именно просмотренный документ. Подпись не является access token
и не предоставляет доступ к файлам.

Назначение файла выбирает сотрудник, автоматической классификации «договор /
приложение» по имени или содержимому нет. При создании файлы показываются списком:
имя с предпросмотром, размер, удаление и две независимые отметки — «Скрыть от
контрагентов» и «Выделить спецификацию». По умолчанию все новые файлы скрыты,
а для выделения отмечен первый загруженный файл; остальные можно включить вручную.
Для выделения отмечать нужно именно файлы
с таблицами товаров, включая приложения к договору, если позиции находятся в них.
Файлы без отметки выделения не передаются парсеру. Видимость не зависит от выделения:
скрытый файл сохраняется только в `request_hidden_files`; при снятии отметки
скрытия исходный файл сохраняется только в публичных `request_files`, становится
доступным контрагентам с доступом к заявке и входит в почтовые вложения.
Хотя бы один файл должен участвовать в формировании. В подтверждении показан
список выбранных файлов. В multipart подготовки `extraction_indices` задаёт
нулевые индексы среди `files`; отсутствие поля сохраняет обработку всех исходников
для совместимости API. `public_source_indices` задаёт индексы исходников, для которых
снята отметка скрытия; отсутствие поля означает, что все исходники скрыты.
Серверная подпись связывает выбор видимости, выделения и все исходники, включая
необрабатываемые приложения: изменение любой галочки или файла требует повторной
подготовки. При создании backend берёт видимость из проверенной подписи.
В подтверждении и предпросмотре писем показан фактический набор публичных файлов.

Спецификация — новый DOCX: наименование товара/работы/услуги, количество,
единица измерения, артикул, технические характеристики и комплектность.
Заголовок внутри документа и его метаданные — «Заявка на закупку».
Имя файла — `Заявка на закупку {номер заявки}.docx`. Номер передаётся при подготовке
и входит в серверную подпись вместе с именем файла; изменение номера требует
повторной подготовки. Небезопасные для имени файла символы номера заменяются `_`.
Оборудование/объект из объединённых ячеек сохраняется для каждой позиции.
Неизвестные столбцы, цены, суммы, НДС и реквизиты не переносятся. Исходные стили,
колонтитулы, комментарии, подписи, изображения и метаданные не копируются.
Экономист обязательно сравнивает результат с исходниками перед подтверждением.
Поддерживается табличная спецификация с распознаваемыми русскими заголовками;
произвольное описание предмета договора в прозе автоматически не преобразуется.
Распознаются переносы в заголовках (включая «Кол-во»). Продолжение таблицы без
шапки связывается с предыдущей страницей по числу и геометрии столбцов.
Продолжение наименования на следующей странице дополняет прежнюю позицию,
не создавая отдельную строку и не теряя её количество. Позиции не дедуплицируются.
Текстовый слой PDF имеет приоритет перед OCR: фоновые изображения и водяные знаки
не должны заменять исходный текст распознанным. При конфликтующих линиях таблицы
восстанавливается видимая сетка, а содержимое берётся из исходного текста.
Формулы XLSX не выполняются: используются сохранённые значения; отсутствие
результата формулы в разрешённом поле блокирует подготовку.

Парсер выполняется в отдельном ограниченном по времени процессе backend,
без нового runtime-сервиса и очередей. OCR использует локальные языковые данные
Tesseract для русского и английского; документы не отправляются внешним сервисам.
Неподдерживаемая структура, нераспознанная таблица и недоступный OCR блокируют
подготовку; исходник никогда не используется как публичный fallback.

`request_hidden_files` связывает скрытые оригиналы с заявкой. `request_files` содержит
спецификацию и публичные вложения, включая нормативный документ и исходники,
для которых сотрудник явно снял отметку скрытия.
В `request_hidden_files.is_specification_source` сохраняется назначение скрытого
файла: `true` — участвовал в выделении ТЗ, `false` — обычное скрытое вложение.
Значение берётся из проверенной серверной подписи, а не из отдельного параметра
создания заявки. Для исторических записей `NULL` означает неизвестное назначение:
до этой миграции выбор выделения не сохранялся. Новые записи получают явный boolean;
при загрузке скрытого файла после создания заявки используется `false`.
Видимость не зависит от флага: все строки этой таблицы закрыты контрагентам.
Списки исходников и скачивание проверяют ту же область заявки, что её детали,
с безусловным запретом контрагенту. Почтовые вложения читаются только из
`request_files`. Новые permissions и ограничения только для экономистов не вводятся.

## Ввод в эксплуатацию

На БД версии 1.0.8 применить единую миграцию `V1.0.9__request_hidden_files.sql`,
затем обновить backend и web. Она сразу создаёт `request_hidden_files`,
`is_specification_source`, ограничения, индекс и комментарии.
Две предварительные локальные миграции создания/переименования объединены до
публикации. Если они уже применены в другом окружении, сначала проверить итоговую
схему и согласовать историю Flyway с объединённой версией; повторно выполнять
`CREATE TABLE` поверх готовой таблицы нельзя. Локальная история согласована,
существующие связи и значения `NULL` сохранены.
Образ backend содержит зависимости разбора и языковые пакеты OCR. Лимит загрузки
остаётся 5 МиБ на файл, до 5 исходников и 15 МиБ суммарно. Обработка ограничена
40 страницами PDF, 2000 строками таблицы, 1000 итоговыми позициями и 120 секундами.
Для сканов перед OCR удаляется растровая сетка, затем её геометрия используется
для восстановления столбцов. Разрешение до 300 dpi ограничено 16 млн пикселей;
неоднозначные количества повторно читаются из изображения ячейки в числовом режиме.
Если количество определить не удалось, частичная спецификация не публикуется.
В подтверждении показываются число позиций и предупреждение о распознавании скана.
Одновременно обрабатываются до двух документов
на backend worker. Gateway допускает до 21 МиБ multipart и ожидает до 150 секунд
только на маршрутах подготовки спецификации и создания заявки.
Существующие вложения автоматически не переклассифицируются: проверка ранее
опубликованных договоров требует отдельной инвентаризации.

В уже созданной заявке `POST /requests/{request_id}/source-files` добавляет один
закрытый исходник за вызов. Требуются доступ к исходникам этой заявки и действующее
право загрузки файлов с областью редактирования (как у публичных вложений).
Кнопка в разделе «Скрытые файлы заявки» зависит от backend action `can_upload_files`.
Раздел скрытых файлов и поле «План заявки» находятся внутри основной карточки заявки.
План расположен после информационных блоков, перед нижними действиями карточки.
Скрытые файлы оформлены такими же чипами, как публичные вложения; добавление —
кнопкой с плюсом. Пояснения о доступе, размере и выделении собраны в info-иконке,
доступной наведением, фокусом с клавиатуры и касанием. Назначение конкретного файла
показано в подсказке его чипа; в общей info-подсказке список файлов не дублируется.
После создания заявки добавление и удаление файлов доступны только в режиме
«Изменить», по backend actions загрузки/удаления. Новые файлы и удаления сначала
показываются как изменения формы: «Сохранить» отправляет запросы, «Отмена» отменяет
несохранённые изменения списка. Успешные операции не повторяются при повторе
частично неудачного сохранения. Новый скрытый файл загружается без настроек
выделения спецификации; назначение сохраняется как `is_specification_source=false`.
Привязка к плану редактируется общим сохранением
карточки по действующему backend action редактирования.
Файл проходит общий guard, сохраняется только в `request_hidden_files` и не меняет
готовую заявку; парсер и уведомления контрагентам не запускаются. Лимит — 5 МиБ на
файл; ограничения 5 исходников / 15 МиБ относятся к единовременной подготовке.
Gateway допускает до 6 МиБ multipart на маршруте закрытых исходников, чтобы
служебные поля не уменьшали допустимый размер файла.
Маршруты `/source-files` сохранены для совместимости API; они возвращают скрытые
файлы с полями `is_specification_source` (`true` / `false` / `null`) и `can_delete`.
Удаление `DELETE /requests/{request_id}/source-files/{file_id}` требует чтения этой
заявки, права удаления и области редактирования. Разрешены только скрытые файлы с
`is_specification_source=false`; `true` и исторический `null` защищены на сервере.
Связь блокируется на время проверки и условного удаления в транзакции UoW;
файл/объект хранилища удаляется только при отсутствии других связей.
На чипе файла в подсказке показано
назначение: «Исходник для ТЗ», «Скрытое вложение» или «Назначение неизвестно».
Обычный `POST /requests/{request_id}/files` сохраняет контракт публичных вложений.
Предпросмотр и создание работают без почты.
