# Пять ролей — сценарии тестирования без почты

47 связанных сценариев вместо 209 отдельных проверок. Ветка without_keycloak_and_others@cb46f68. Основные пользователи заранее внесены в БД и готовы ко входу, почта недоступна.

Исключены только отправка/получение писем, приглашения по почте, подтверждение email, установка/восстановление пароля по письму, почтовые ответы, рассылки и IMAP. Новые записи через интерфейс проверять до сохранённой карточки; первый вход по письму не выполнять. Полный сценарий внешнего контрагента, включая фактический вход скрытого контрагента, требует отдельной роли; здесь проверяются сохранение скрытия и запрет ручного КП скрытому контрагенту.

## Маршруты и порядок работы

Вход готового пользователя: /login → /api/v1/auth/login → /iam/authorize → /iam/login → /api/v1/auth/callback → рабочая область. /auth/login и /auth/callback — дополнительные маршруты интерфейса. Создание сотрудника: /admin → «Создать сотрудника» → заполнить доступные поля/роль/юнит → сохранить. Ручной контрагент: /contractors → создание; для АД — вкладка контрагентов в /admin. Публичные /register, /auth/registration-link-status и /verify-email проверяются без действующего почтового токена только на корректное отображение ошибок.

АД и РП закрепить за корнем А; ВЭ — над группами А1 и А2; Э — за А1. В А1.1 подготовить подчинённого для проверок управления. В Б — отдельные сотрудники, заявки и контрагенты для отрицательных проверок. СА имеет глобальную область; проверку входа без юнита выполнить отдельно, а для создания ручных контрагентов с привязкой к А закрепить СА за А. Основные пять аккаунтов не использовать для блокировок/смены роли; для этого нужен запасной сотрудник с готовым паролем. Перед проверками экранов индивидуальные расширения сняты.

Выполнять сценарии по порядку. Обозначение «основной проход» означает полный сценарий одной ролью; для остальных проверять только указанные различия прав, повторно весь сценарий не проходить. Где написано «все пять ролей» или требуется действие каждой роли — выполнить для каждой. Поиск, фильтры и обновление уже включены в сценарии сущностей и отдельно не дублируются. В результат записать статус «Пройдено», «Ошибка» или «Заблокировано», факт и номер дефекта; при различиях указать роль и не прошедший шаг. Нет исходных данных — «Заблокировано». После смены роли/юнита/прав обновлять сессию новым входом. Статусы и разрушительные действия проверять на запасных записях, чат — до закрытия заявки. Критичная — вход, доступ, целостность и ключевые операции; высокая — остальные рабочие операции; средняя — удобство навигации.
