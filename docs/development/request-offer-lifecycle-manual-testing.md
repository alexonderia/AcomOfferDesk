# Ручная проверка распределения заявок и жизненного цикла КП

`AOD-BL-002` — Specification Sync / Regression Protection, а не production defect.

## Подготовка

Создайте Contractor с правами просмотра открытых заявок и создания/редактирования КП. Привяжите его и Operator к root unit `A`. Подготовьте сотрудника, которому доступно штатное назначение в `A`, и сотрудника в другой root unit `B`. Для всех шагов фиксируйте HTTP-статус в DevTools Network: интерфейс не является источником авторизации.

## SMOKE-003 / REQ-003

1. Operator создаёт открытую заявку с обязательной начальной суммой, нормативным документом и файлом.
2. Contractor открывает список заявок, прямой contractor-view и пытается создать КП по известному ID.
3. Выполните обычное действие назначения и назначьте ответственным сотрудника из `A`; повторите все три действия.
4. Назначьте ответственным сотрудника из `B`; повторите проверку.

Ожидание: пока текущий owner имеет роль Operator, в списке нет строки, direct view и POST создания КП не раскрывают заявку (`404`) даже при общем root unit. После штатного назначения сотрудника не-Operator из общего root scope `A` заявка видна и для неё можно создать первое КП. При ответственном из `B` доступ отсутствует. Роль Operator — отрицательный признак операторского этапа; она не является whitelist ролей для публикации.

## REQ-007

1. Для видимой Contractor заявки добавьте Contractor в hidden list.
2. Повторите список, direct view, POST КП и скачивание файла заявки по прямому URL.
3. Уберите Contractor из hidden list и повторите проверку.

Ожидание: при hidden-флаге заявка не обнаруживается и её файл не скачивается; после снятия hidden-флага доступ восстанавливается при общем root scope и выполненном штатном распределении.

## OFFER-001 / OFFER-002

1. На опубликованной открытой заявке создайте КП с суммой и файлом.
2. Повторите POST создания КП из второй вкладки или API-клиента тем же Contractor.
3. Переведите заявку в `closed` или `cancelled` и повторите POST, изменение суммы и добавление/удаление файла у уже созданного КП.
4. На открытой заявке после создания КП переназначьте владельца на Operator в том же root scope. Откройте собственное workspace КП и обновите страницу.

Ожидание: создаётся одно активное КП на пару request/contractor; параллельные повторные POST не создают второй активный экземпляр. Закрытая/отклонённая заявка не принимает новое КП и перечисленные изменения существующего КП (`409`, состояние не меняется). Уже созданное собственное КП не исчезает только из-за переназначения владельца на Operator; это исторический доступ, а не повторная публикация заявки.

## OFFER-007

Проверьте PATCH статуса КП из `submitted`, `accepted`, `rejected` и `deleted` каждой ролью, имеющей или не имеющей соответствующее право, на открытой и закрытой заявках.

Ожидание текущего контракта: разрешены только статусы `submitted`, `accepted`, `rejected`, `deleted`; для `accepted`/`rejected` действует специальный department-scope путь, а при его отсутствии требуется `offers.status.update` и обычная проверка scope. Ограничение по паре source→target в коде не определено: его нельзя считать бизнес-правилом без отдельного решения. Для `closed`/`cancelled` все изменения статуса отклоняются до записи.

## WORK-001 / WORK-003

1. Contractor открывает workspace собственного КП, затем staff закрывает заявку в другой сессии.
2. Contractor пытается изменить сумму, статус или файл из оставшейся открытой вкладки.
3. Contractor открывает workspace чужого КП и workspace собственного КП после переназначения владельца на Operator в том же root scope.

Ожидание: чтение собственного исторического workspace сохраняется в допустимом scope; stale mutations после закрытия не выполняются и не показывают ложный успех. Чужой workspace не открывается. При изменении роли, root scope или hidden-флага результат определяется повторной серверной проверкой на каждом запросе.
