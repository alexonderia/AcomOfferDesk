# Работа без почтового сервиса

## Включение режима

Установить `EMAIL_ENABLED=false` в общем runtime env приложения, указанном в `APP_RUNTIME_ENV_FILE`. Его читают **backend и notifications_worker**. Одного `--env-file` для подстановок Compose недостаточно, если он отличается от runtime env. Пересоздать оба сервиса с одной конфигурацией; при обновлении backend выполнить штатное обновление gateway. IAM продолжает работать со своими настройками. Интерфейсу отдельный build-time флаг не нужен.

При `false` не требуются `EMAIL_ADDRESS`, `EMAIL_APP_PASSWORD`, `SMTP_HOST`, `EMAIL_VERIFICATION_SECRET`. IAM, PostgreSQL, MinIO и RabbitMQ по-прежнему нужны для соответствующих функций приложения.

Флаг по умолчанию `true`. Сбой SMTP сам по себе режим не переключает. Для возврата к `true` заполнить почтовые настройки и пересоздать оба сервиса. Ранее созданные готовые аккаунты сохраняют пароли и статус.

## Поведение

- UI получает `email_enabled`, `direct_user_creation`, `password_change` из `GET /api/v1/auth/capabilities`; признак почтового режима также входит в session DTO.
- Обычные сообщения не публикуются для почтовой отправки, секретные ссылки не отправляются напрямую через SMTP, IMAP polling не запускается. Worker не потребляет очередь почты. Уже накопленная очередь сохраняется и может быть обработана после включения почты.
- Явные почтовые действия (recovery, запрос подтверждения, новые приглашения, рассылка заявки) возвращают объяснение недоступности. Новые токены/вложения для отключённого действия не готовятся. Существующие ссылки обрабатываются по прежним правилам срока действия.
- Внутренние уведомления, realtime, чат и бизнес-операции сохраняются. Настройки уведомлений показывают недоступность email, сохраняя прежние настройки до повторного включения сервиса.
- Режим не подтверждает email автоматически и не меняет требования одобрения существующей саморегистрации `review`.

## Создание пользователя

В администрировании выбрать допустимую роль и подразделение, указать логин, начальный пароль и повтор. Email необязателен. Новый пароль — **12–128 символов**, пробелы значимы. Права создания и область проверяет backend.

`POST /api/v1/users/register` принимает `password` и `password_confirmation` только при отключённой почте. IAM хранит Argon2-хеш; бизнес-БД пароль не получает. Новый аккаунт готов к входу без обязательного письма и `complete_profile`. Источник выдачи доступа записывается в IAM-аудит.

В форме ручного контрагента поля доступа необязательны: их заполняют вместе, если нужен вход. Справочную карточку для ручного КП можно создать без пароля. Переиспользование существующей компании не выдаёт права на инициализацию её credentials. Для такой записи требуется отдельное штатное восстановление доступа, когда оно доступно; смена собственного пароля требует уже известного текущего пароля.

Повтор создания не сбрасывает пароль и не снимает блокировку. IAM допускает повтор прямого создания только для той же identity, созданной этим способом, с совпадающими логином, ролью и действующим паролем. После смены пароля старые реквизиты создания повторять нельзя.

## Самостоятельная смена пароля

Открыть **«Профиль» → «Изменение пароля»**, указать текущий пароль, новый и повтор нового, нажать **«Сохранить пароль»**. Форма находится внутри профиля, включая профиль СА; отдельной кнопки в навигации и дополнительного окна нет. При закрытии профиля введённые пароли очищаются. Операция работает и с включённой почтой.

У каждого парольного поля есть кнопка «глаз»: она показывает или скрывает только это поле, не отправляя форму и не меняя значение. По умолчанию пароли скрыты. Переключатель также доступен при задании пароля сотруднику/контрагенту; на странице входа он уже предусмотрен.

`POST /api/v1/users/me/password` берёт account/session ID из авторизации. IAM проверяет принадлежность и состояние сессии и текущий пароль. При неверном пароле данные не меняются. Применяются CSRF и ограничение частоты; секреты исключены из ответов валидации и аудита.

После успеха IAM отзывает refresh-сессии и незавершённые setup/reset-токены, cookie текущего клиента очищаются, необходим новый вход. IAM browser session тоже становится недействительной. Выданные access JWT других клиентов действуют до `exp` (по умолчанию 300 секунд); локальная проверка backend не выполняет онлайн-интроспекцию каждой сессии.

## Миграция и данные

Перед запуском новой версии backend применить `V1.0.8__qa_feedback_and_chat_unit_scope.sql` основной БД: новые поля обратной связи, provider `iam`, синхронизация участников чата по units и пересчёт существующих чатов. Новых IAM-миграций нет.

Миграция добавлена в локальный источник `../order_database/flyway/sql` и идентичный снимок `deploy/order_database/flyway/sql`. Исторические наборы миграций этих репозиториев различались до изменения. Перед выпуском сверить Flyway `info` и `validate` с историей **конкретной БД**; старые миграции/checksums автоматически не заменять и `repair` для подавления расхождения не запускать. Применение и восстановление выполняются по [runbook БД](order-database-vps.md) с резервной копией. Проверить новую функцию на копии PostgreSQL до выпуска.

Отчёт без изменения данных:

```powershell
docker exec backend python -m app.scripts.audit_qa_state --check-iam --check-storage
```

Отчёт содержит логины, состояния IAM и доступность нормативов; хранить как служебные данные. Отсутствие binding видно и без `--check-iam`. Проверка файлов использует stat без скачивания содержимого. Недоступность сервиса отличается от отсутствия содержимого.

После проверки отчёта можно восстановить **конкретную** IAM-связь:

```powershell
docker exec backend python -m app.scripts.audit_qa_state --user LOGIN --check-iam --repair-bindings
```

Команда сверяет существующий IAM subject и точный логин, не создаёт аккаунты и не меняет пароли. При отсутствии IAM account возвращается ошибка для отдельного восстановления. Та же проверка используется API роли/статуса при отсутствии активной связи. Норматив без содержимого нужно загрузить повторно из достоверного источника; отчёт его не восстанавливает.

## Сброс пароля пользователя суперадминистратором

В администрировании открыть карточку сотрудника или контрагента → **Сбросить пароль**. Указать новый пароль и повтор (12–128 символов). Старый пароль пользователя не требуется. Действие доступно только суперадминистратору; сброс пароля любой учётной записи суперадминистратора, включая свою, запрещён. Собственный пароль меняется в профиле с проверкой текущего.

`POST /api/v1/users/{user_id}/password/reset` принимает `new_password` и `password_confirmation`, возвращает пустой `204`. Backend проверяет роль инициатора и цель, активную IAM-связь, точное совпадение логина и роли. IAM повторно проверяет действующую сессию и актуальную роль инициатора, защищает учётные записи суперадминистраторов. Наличие произвольных делегированных разрешений не даёт права сброса.

Работает при включённой и отключённой почте. Письма не отправляются. Логин, роли, блокировка/одобрение пользователя и требование заполнить профиль сохраняются; сброс не выдаёт доступ заблокированному или ожидающему одобрения пользователю. При отсутствии активной IAM-связи сначала требуется её восстановление.

Новый пароль хешируется Argon2id; счётчик ошибок входа и временная блокировка пароля очищаются. Прежние refresh-сессии, браузерный вход IAM, незавершённые коды входа и ссылки настройки/восстановления пароля отзываются. Уже выданный access JWT действует до истечения своего TTL (по умолчанию 300 секунд); мгновенное прекращение всех API-запросов по старому JWT не гарантируется. Событие `password.administratively_reset` содержит инициатора и цель без пароля. Новый пароль передаёт пользователю сам суперадминистратор.
