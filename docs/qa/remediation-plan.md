# Полный план изменений AcomOfferDesk

## Цель

Исправить подтверждённые дефекты из `AcomOfferDesk_тесты.docx`, проверить гипотезы по зависимым сценариям и обеспечить создание пользователей и самостоятельную смену пароля без почтового сервиса. Код изменён; фактический статус этапов, проверки и оставшаяся приёмка на стенде описаны в [отчёте выполнения](remediation-progress.md).

Дата: 02.11.2026. Основа анализа: ветка `dev`, коммит `aae863b`.

Работа выполняется самостоятельно, без Trellis и субагентов. Основания решений и участки кода: [remediation-code-findings.md](remediation-code-findings.md).

## Зафиксированные требования

- Пустые результаты тестирования считать успешными: всего 47 сценариев, 34 успешных по этому правилу, 12 отмеченных как непройденные, один частично пройденный — №30.
- Сопоставлять замечания с кодом; отличать подтверждённый механизм от гипотезы о данных стенда.
- В режиме с отключённой почтой уполномоченный сотрудник создаёт пользователя из интерфейса с логином и паролем; пользователь может сразу войти без письма и подтверждения email.
- Пользователь меняет собственный пароль в профиле, указав текущий пароль, новый пароль и подтверждение нового. Почта для этого не нужна, в том числе в ограниченном режиме.
- IAM остаётся единственным владельцем учётных данных и проверки паролей; backend отвечает за бизнес-статусы, оргструктуру и область доступа.
- Исправления сохраняют границы ролей, подразделений, скрытия заявок и запреты повторного КП.
- Не подменять отсутствие данных или отказ ожидаемого ограничения новым дефектом.

## Порядок реализации

P1 — изменения, от которых зависят основные операции и воспроизведение. P2 — следующая очередь. Каждый этап закрывается своими проверками; исправления не объявляются готовыми только по отсутствию ошибки в UI.

### Этап 0. Подготовка и воспроизводимость

1. Зафиксировать актуальный commit, состояние рабочих файлов и различия между локальным кодом и стендом.
2. Подготовить отдельные данные: корни А/Б, группы А1/А1.1/А2, пять ролей, запасной сотрудник, контрагенты, заявки, КП и планы.
3. Для замечаний записать роль, ID, шаг, запрос/ответ API и состояние связей. Проверить IAM bindings/accounts, контакты, org memberships, функцию синхронизации чатов и объекты хранения.
4. Выполнить подходящие исходные проверки затронутых модулей; отделить существовавшие сбои от новых изменений.

Результат: воспроизводимый случай либо явно зафиксированное условие, которого не хватает. Исходные 34 успешных сценария не переводятся в ошибки из-за пустого результата. При ожидаемом отказе исправляются условия проверки и объяснение в UI.

### Этап 1. P1 — привязки IAM и статусы, №7 и №10

Причины: локальная запись может не иметь активной IAM-привязки; переход `review -> active` дополнительно требует права одобрения и подтверждённого основного email.

1. Проверить цепочку «локальный пользователь — provider=iam — IAM account — credentials — бизнес-статус — auth_status».
2. Подготовить проверку/восстановление связей с отчётом до применения. Связывать только проверенные соответствующие аккаунты; действующие пароли сохранять.
3. Обеспечить единое сопоставление статусов и проверку условий до изменения данных; возвращать понятную причину отказа.
4. Учесть частичные ошибки двух БД: повтор восстанавливает согласованность, не создаёт дубликат и не сбрасывает рабочий пароль.
5. Для обычной регистрации сохранить правила подтверждения email. Готовая запись, административно созданная без почты, проходит отдельный сценарий этапа 3.

Участки: `backend/app/api/v1/users.py`, `backend/app/services/users.py`, `backend/app/domain/iam_status.py`, `backend/app/repositories/user_auth_accounts.py`, IAM client и скрипт миграции пользователей.

Приёмка: блокировка запрещает новый вход; восстановленный пользователь входит прежним паролем; подготовленная регистрация одобряется; неподтверждённая обычная регистрация получает ожидаемый отказ; ошибка IAM не выдаёт ложного успеха.

### Этап 2. P1 — явный режим отключённой почты

1. Ввести единый `EMAIL_ENABLED`, по умолчанию `true`; `false` означает ограниченный режим без почты. Backend сообщает UI возможности приложения через общий контракт, включая экран входа.
2. Сделать почтовые настройки условно обязательными: запуск без почты не требует фиктивных SMTP/IMAP реквизитов.
3. При `false` отключить отправку обычной почты через очередь, прямой SMTP для секретных ссылок, IMAP polling и почтовую доставку worker. Существующую очередь не удалять; не допускать доставки при выключенном режиме.
4. Сохранить внутренние уведомления, realtime, чат и бизнес-операции. Пропуск почты не должен откатывать допустимое сохранение или создавать бесконечные повторы.
5. Почтовым действиям показывать причину недоступности; не возвращать ложное «письмо отправлено». Временная ошибка SMTP не переключает режим автоматически.
6. Обновить env examples, compose и инструкции. При повторном включении почты готовые пользователи, созданные без неё, продолжают входить.

Участки: `backend/app/core/config.py`, `backend/app/main.py`, `backend/app/infrastructure/email/`, сервисы почтовых сценариев, `notifications_worker/app/`, `shared/`, общие frontend API-типы и окружения.

Приёмка: без SMTP/IMAP приложение запускается; вход готовых пользователей, заявки, КП, чат и внутренние уведомления работают; обращений к отключённой почтовой инфраструктуре нет.

### Этап 3. P1 — создание пользователя с логином и паролем

1. Расширить существующую форму и `POST /api/v1/users/register` начальным паролем и подтверждением для ограниченного режима. Email сделать необязательным на всех слоях этого сценария.
2. Проверять уникальность логина, разрешённую роль, обязательные для неё данные и подразделение на backend.
3. В IAM реализовать административную инициализацию credentials нового готового аккаунта с общими функциями хеширования. Pending-регистрация не превращается в произвольную замену пароля активного пользователя.
4. Согласовать локальную запись, профиль, членства, IAM account, привязку и статус готовности. Возвращать успех только при готовности к входу.
5. Не запускать почтовые setup/verification/recovery и не оставлять их обязательными на первом входе. Непроверенному адресу не присваивать фиктивный признак подтверждения; административное создание фиксировать в аудите.
6. Для контрагента, которому нужен вход, дать соответствующие поля в его форме. Создание справочной карточки для ручного КП не требует обязательной выдачи доступа и пароля.
7. Предусмотреть повтор после таймаута/частичного сохранения: без второго пользователя, захвата занятого логина, активации заблокированной записи или замены чужого рабочего пароля.

Участки: `backend/app/schemas/auth.py`, `backend/app/api/v1/auth.py`, `backend/app/services/users.py`, IAM client, `iam/iam_app/{api,schemas,services}.py`, `web/src/features/admin/`, формы контрагентов и `web/src/shared/api/auth/registerUser.ts`.

Приёмка: уполномоченный сотрудник создаёт пользователя без email; тот сразу входит с заданными данными и правильной областью. Неправильная роль/чужой юнит, занятый логин и некорректные пароли не создают ошибочный доступ. После включения почты аккаунт продолжает работать.

### Этап 4. P1 — самостоятельная смена пароля

1. Добавить authenticated backend-операцию и соответствующую внутреннюю операцию IAM. Account ID брать из подтверждённой сессии/привязки; менять чужой пароль этим действием нельзя.
2. IAM проверяет текущий пароль, новый пароль и подтверждение; сохраняет хеш и результат в аудите без секретов.
3. Использовать действующую политику нового пароля — сейчас 12–128 символов. Пароли не обрезать как обычный текст. Неверный текущий пароль и ошибки нового ничего не меняют.
4. Применить штатный механизм отзыва сессий IAM и очистки текущих cookie; после успеха клиент выполняет повторный вход. Для уже выданных access tokens учитывать существующий срок действия.
5. Разместить форму «Текущий пароль / Новый пароль / Повтор нового пароля» непосредственно в профиле. По уточнению от 03.11.2026 профиль доступен также СА на компьютере и мобильном экране; отдельная кнопка/окно смены пароля не используются.
6. Использовать CSRF и ограничение частоты; исключить текущий и новый пароли из ответов, логов, аудита и очередей. Очищать поля формы после завершения.

Участки: IAM services/API/schemas/audit, `backend/app/infrastructure/iam_client.py`, users API/schemas, `web/src/shared/components/ProfileButton.tsx`, меню учётной записи и общий API-клиент.

Приёмка: операция работает в обоих режимах, без писем и почтовых токенов; старый пароль после успешной смены отклоняется, новый принимается; при неверном старом пароле учётная запись не меняется.

## Миграции и восстановление данных

- Обязательная миграция — автор и время обратной связи, индексы под подтверждённые запросы списка.
- При подтверждении причины чата — новая версия функции синхронизации и контролируемый пересчёт существующих участников.
- Основная схема управляется внешним `order_database`; новые миграции согласуются с источником и отражаются в `deploy/order_database/flyway/sql` по существующему процессу. Применённые миграции не переписываются.
- Дополнительные поля происхождения административной активации/состояния операции вводятся только при подтверждённой необходимости; сначала используются имеющиеся статусы и аудит.
- Восстановление IAM-связей, компаний и файлов начинается с отчёта затронутых записей. Не выполнять массовый сброс паролей, автоматическое слияние неоднозначных компаний и удаление истории.
- До применения миграций на стенде обеспечить штатный способ восстановления данных и проверить совместимость версий backend/IAM/web.

## Проверки и выпуск

1. Для каждого этапа добавить проверки изменённых контрактов и найденной причины: backend unit/integration, IAM tests и frontend component/API tests по затронутым слоям.
2. Чат и SQL-участников проверять с настоящей БД: подмена бизнес-сервиса не покрывает расхождение оргструктуры и SQL-функции.
3. Для режима без почты проверять отсутствие обоих путей почтовой отправки и IMAP при сохранении внутренних уведомлений.
4. Обязательный ручной сценарий: запуск с `EMAIL_ENABLED=false` без SMTP/IMAP → создание пользователя без email → вход → смена пароля → повторный вход → блокировка/восстановление → включение почты → повторный вход.
5. Отдельно проверить неверный текущий пароль, несовпадающее подтверждение, недопустимый новый пароль, занятый логин, запрещённую роль/чужой юнит и повтор после таймаута. Ни один отказ не должен менять чужие credentials или создавать ошибочный доступ.
6. Повторить исходные 47 сценариев как регрессию. Для №22/28/45 сначала устранить связанные блокировки; №26 использовать с правильным планом. Новые проверки создания/смены пароля добавить отдельными пунктами.
7. Записывать итоговые «Пройдено / Ошибка / Заблокировано» с ролью, ID, фактом и исправлением. Внешние блокировки отмечать явно, не выдавая их за успешную проверку.
8. Перед итоговой приёмкой выполнить backend/IAM регрессию, frontend lint/unit/build и проверку compose затронутых окружений. Повторять широкий прогон после новых изменений либо перед выпуском.
9. Обновить документацию окружений, жизненного цикла аккаунтов, permissions/actions, миграций и QA-чеклист. Реальную доставку писем проверить отдельным прогоном после включения почты.

Изменения вносятся последовательно по этапам, проверяемыми частями. Новые доказанные причины фиксируются в этом документе до расширения объёма работ.

## Границы

- По поручению пользователя реализованы изменения кода, применена локальная миграция и проведены сквозные проверки с отдельными QA-данными. VPS и исходный внешний стенд не обновлялись. [Протокол](runtime-verification-2026-11-02.md).
- Полная проверка почтовой доставки и внешнего интерфейса контрагента требует отдельного прогона.
- Отсутствие права экономиста создавать корневой план и отсутствие права РП отправлять чат не устраняются расширением базовых прав.
- Не создавать новый провайдер аутентификации и не хранить пароли в бизнес-БД.
